Links dazu, wie du eine iOS-, Flutter- oder React-Native-App strukturierst: zuerst die offiziellen Vorgaben, dann die Bibliotheken, Beispiel-Apps und Werkzeuge, die sie in die Praxis umsetzen. Jeder Eintrag wurde von einer Person geöffnet und gelesen und kommt mit einer Zeile, die sagt, was du davon hast. Ein wöchentlicher Job markiert jedes gelistete Repository, das archiviert, umbenannt oder seit 540 Tagen nicht aktualisiert wurde, sowie jeden Link, der nicht mehr antwortet, damit die Liste nicht unbemerkt veraltet.

## Highlights

- **Drei Plattformen, eine Struktur** — Abschnitte für iOS, Flutter und React Native mit denselben Kategorien, dazu die plattformunabhängigen Artikel, aus denen die Muster stammen.
- **Ein Grund für jeden Link** — jeder Eintrag hat ein einzeiliges „Warum“; Marketingwörter wie „beste“ lehnt der Checker ab.
- **Geprüft, nicht gesammelt** — die Einträge liegen in [data/entries.json](data/entries.json), werden bei jedem Push validiert und in dieses README gerendert; GitHub-Aktivität und Link-Zustand werden jede Woche geprüft ([so geht’s](docs/guides/keeping-the-list-current.md)).
- **Dieselbe Funktion in drei Stacks** — ein [Beispiel für eine Leseliste](Examples/README.md) in SwiftUI, Flutter und React Native mit 43 Tests, die auf jeder Plattform dieselben Regeln prüfen.
- **Aktuelle Plattformänderungen** — eine [Anleitung zur iOS-27-Anforderung für den Scene-Lebenszyklus](docs/guides/ios-27-scene-life-cycle.md) für native Apps sowie Flutter- und React-Native-Apps.

## Schnellstart

**1. Wähle deine Plattform.** Springe zu [iOS](#ios), [Flutter](#flutter) oder [React Native](#react-native). Lies zuerst die Einträge unter *Offizielle Vorgaben*; die Bibliotheken darunter bauen auf diesen Ideen auf.

**2. Führe das Beispiel für deinen Stack aus.** Es ist die kleinste lauffähige Version der Struktur, die die Anleitungen beschreiben:

```sh
git clone https://github.com/muhittincamdali/awesome-mobile-architecture.git
cd awesome-mobile-architecture/Examples/flutter/reading_list   # or ios/ReadingList, react-native/reading-list
flutter test                                                  # swift test, or npm ci && npm test
```

**3. Entscheide, wie viel Struktur du brauchst.** [Eine Architektur wählen](docs/guides/choosing-an-architecture.md) ordnet die gemeinsamen Ideen der drei Plattformen und sagt, ab wann sich eine Bibliothek wie TCA, Bloc oder Redux Toolkit lohnt.

## Konzepte, die überall gelten

### Offizielle Vorgaben

- [Guide to app architecture (Android)](https://developer.android.com/topic/architecture) - Googles Leitfaden zu UI-Schicht, Datenschicht und unidirektionalem Datenfluss; dieselbe Aufteilung wird bei iOS, Flutter und React Native verwendet.
- [Presentation Model](https://martinfowler.com/eaaDev/PresentationModel.html) - Das Muster, aus dem MVVM entstand: Zustand und Verhalten der View in einer Klasse, die du ohne UI testen kannst.
- [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) - Der Originalartikel zur Abhängigkeitsregel zwischen den Schichten, auf dem die meisten Clean-Architecture-Vorlagen für Mobile aufbauen.
- [The Elm Architecture](https://guide.elm-lang.org/architecture/) - Model, update, view: die unidirektionale Schleife hinter TCA, Redux und BLoC, erklärt auf wenigen kurzen Seiten.

## iOS

### Offizielle Vorgaben

- [Discover Observation in SwiftUI](https://developer.apple.com/videos/play/wwdc2023/10149/) - WWDC23-Session dazu, wie Observation die Properties verfolgt, die eine View liest – die Grundlage heutiger SwiftUI-ViewModels.
- [Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app) - Apples Schritt-für-Schritt-Erklärung zu `@Observable`-Modellen und dazu, wer sie mit `@State`, `@Environment` und `@Bindable` besitzt.
- [Migrating to the Observable macro](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro) - Die genauen Änderungen, mit denen ein `ObservableObject`-ViewModel zu `@Observable` wird, und wie sich die View-Updates ändern.
- [Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/) - Datenrennen-Sicherheit, `Sendable` und Actor-Isolation Schritt für Schritt: die Regeln, an die sich jede Swift-6-Architektur halten muss.
- [TN3187 UIKit scene-based life cycle](https://developer.apple.com/documentation/technotes/tn3187-migrating-to-the-uikit-scene-based-life-cycle) - Apples Technote zum Umstieg einer App, die nur einen App Delegate nutzt, auf `UIScene`; Apps, die mit dem iOS-27-SDK gebaut werden, müssen es einsetzen.

### Bibliotheken für State und Architektur

- [Swift Async Algorithms](https://github.com/apple/swift-async-algorithms) - Debounce, Throttle, Merge und weitere `AsyncSequence`-Operatoren, die in ViewModels Combine-Pipelines ersetzen.
- [Swift Sharing](https://github.com/pointfreeco/swift-sharing) - Teilt und speichert State zwischen Features (User Defaults, Dateien, Speicher) über einen einzigen Property Wrapper.
- [The Composable Architecture](https://github.com/pointfreeco/swift-composable-architecture) - Reducer, Effects und Dependencies in einer Bibliothek, mit einem Test Store, der jede Zustandsänderung prüft.
- [Workflow (Swift)](https://github.com/square/workflow-swift) - Squares komponierbare State Machines, die UI rendern, mit einer passenden Kotlin-Bibliothek für die Android-App.

### Dependency Injection

- [Factory](https://github.com/hmlongco/Factory) - Container-basierte Injection mit zur Compile-Zeit geprüften Registrierungen und Überschreibungen pro Test, ohne Codegenerierung.
- [Needle](https://github.com/uber/needle) - Ubers zur Compile-Zeit geprüfter Dependency-Graph, aus Code generiert und für Apps mit vielen Modulen gebaut.
- [Swift Dependencies](https://github.com/pointfreeco/swift-dependencies) - Dependency Injection im Environment-Stil, die auch außerhalb von Views funktioniert und pro Test Testwerte einsetzt.
- [Swinject](https://github.com/Swinject/Swinject) - Laufzeit-Container mit Objekt-Scopes, üblich in UIKit-Codebasen, die Abhängigkeiten beim Start auflösen.

### Navigation

- [Swift Navigation](https://github.com/pointfreeco/swift-navigation) - Zustandsgetriebene Navigation für SwiftUI, UIKit und AppKit: Ein Ziel ist ein Optional oder ein Enum-Case im Modell.
- [XCoordinator](https://github.com/QuickBirdEng/XCoordinator) - Coordinator-Muster für UIKit mit typisierten Routen, damit View Controller einander nicht mehr pushen.

### Beispiel-Apps

- [Clean Architecture for SwiftUI](https://github.com/nalexn/clean-architecture-swiftui) - SwiftUI-App mit SwiftData-Persistenz, Netzwerk, Dependency Injection und Unit-Tests in getrennten Schichten.
- [iOS Clean Architecture MVVM](https://github.com/kudoleh/iOS-Clean-Architecture-MVVM) - UIKit-Vorlage mit DI-Container, Flow-Coordinators, DTO-Mapping und Response-Caching über alle Schichten hinweg.
- [TCA example apps](https://github.com/pointfreeco/swift-composable-architecture/tree/main/Examples) - Fallstudien sowie die Apps Todos, Voice Memos, SyncUps und Search, die mit jedem Release der Bibliothek aktuell gehalten werden.

### Tests

- [SnapshotTesting](https://github.com/pointfreeco/swift-snapshot-testing) - Zeichnet Views und Werte als Referenzdateien auf und schlägt bei Änderungen fehl – so fallen UI-Regressionen auf, die Unit-Tests übersehen.

### Projektstruktur und Tooling

- [Tuist](https://github.com/tuist/tuist) - Erzeugt Xcode-Projekte aus Swift-Manifesten und hält so die Modulgrenzen explizit, während die App wächst.

## So werden Einträge ausgewählt

Ein Eintrag wird aufgenommen, wenn er hilft, eine App zu strukturieren, und eine Person ihn gelesen hat – nicht, weil er beliebt ist. Er braucht:

- eine offizielle Quelle oder eine Bibliothek, ein Beispiel oder einen Artikel, der ein Muster in funktionierendem Code zeigt;
- bei einem GitHub-Repository: nicht archiviert und ein Push innerhalb der letzten 540 Tage;
- eine einzeilige Begründung, die in einfachen Worten sagt, was der Leser davon hat.

Einträge, die diese Regeln später nicht mehr erfüllen, werden entfernt oder ersetzt. Bekannte Lücken: Reines Android- und Kotlin-Multiplatform-Material liegt außerhalb des Umfangs, und kostenpflichtige Kurse werden nicht aufgeführt.
