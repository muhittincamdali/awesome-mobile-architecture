Enlaces sobre cómo estructurar una app de iOS, Flutter o React Native: primero la guía oficial y después las bibliotecas, apps de ejemplo y herramientas que la llevan a la práctica. Una persona abrió y leyó cada entrada, y todas incluyen una línea que explica qué obtienes de ella. Una tarea semanal señala los repositorios listados que estén archivados, renombrados o sin actualizar desde hace 540 días, y los enlaces que dejen de responder, para que la lista no se pudra sin que nadie se dé cuenta.

## Lo más destacado

- **Tres plataformas, una estructura** — secciones de iOS, Flutter y React Native con las mismas categorías, además de los artículos independientes de la plataforma de los que salen los patrones.
- **Una razón para cada enlace** — cada entrada tiene un "porqué" de una línea; el verificador rechaza palabras de marketing como "el mejor".
- **Verificado, no recopilado** — las entradas están en [data/entries.json](data/entries.json), se validan en cada push y se generan en este README; la actividad en GitHub y el estado de los enlaces se comprueban cada semana ([cómo](docs/guides/keeping-the-list-current.md)).
- **La misma función en tres stacks** — un [ejemplo de lista de lectura](Examples/README.md) en SwiftUI, Flutter y React Native con 43 pruebas que comprueban las mismas reglas en cada plataforma.
- **Cambios recientes de la plataforma** — una [guía sobre el requisito del ciclo de vida de escenas de iOS 27](docs/guides/ios-27-scene-life-cycle.md) para apps nativas, Flutter y React Native.

## Inicio rápido

**1. Elige tu plataforma.** Ve a [iOS](#ios), [Flutter](#flutter) o [React Native](#react-native). Lee primero las entradas de *Orientación oficial*; las bibliotecas que vienen después se apoyan en esas ideas.

**2. Ejecuta el ejemplo de tu stack.** Es la versión funcional más pequeña de la estructura que describen las guías:

```sh
git clone https://github.com/muhittincamdali/awesome-mobile-architecture.git
cd awesome-mobile-architecture/Examples/flutter/reading_list   # or ios/ReadingList, react-native/reading-list
flutter test                                                  # swift test, or npm ci && npm test
```

**3. Decide cuánta estructura necesitas.** [Elegir una arquitectura](docs/guides/choosing-an-architecture.md) relaciona las ideas comunes a las tres plataformas e indica cuándo una biblioteca como TCA, Bloc o Redux Toolkit empieza a compensar.

## Conceptos que valen en cualquier plataforma

### Orientación oficial

- [Guide to app architecture (Android)](https://developer.android.com/topic/architecture) - Guía de Google sobre la capa de UI, la capa de datos y el flujo de datos unidireccional; la misma división se usa en iOS, Flutter y React Native.
- [Presentation Model](https://martinfowler.com/eaaDev/PresentationModel.html) - El patrón del que nació MVVM: el estado y el comportamiento de la vista en una clase que puedes probar sin UI.
- [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) - El artículo original sobre la regla de dependencia entre capas, en el que se basan la mayoría de las plantillas móviles de clean architecture.
- [The Elm Architecture](https://guide.elm-lang.org/architecture/) - Model, update, view: el bucle unidireccional detrás de TCA, Redux y BLoC, explicado en unas pocas páginas breves.

## iOS

### Orientación oficial

- [Discover Observation in SwiftUI](https://developer.apple.com/videos/play/wwdc2023/10149/) - Sesión de la WWDC23 sobre cómo Observation rastrea las propiedades que lee una vista, la base de los view models actuales de SwiftUI.
- [Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app) - Explicación paso a paso de Apple sobre los modelos `@Observable` y quién los posee con `@State`, `@Environment` y `@Bindable`.
- [Migrating to the Observable macro](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro) - Los cambios exactos para pasar un view model `ObservableObject` a `@Observable` y cómo cambia la actualización de las vistas.
- [Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/) - Seguridad frente a data races, `Sendable` y aislamiento de actors paso a paso: las reglas a las que debe ajustarse toda arquitectura Swift 6.
- [TN3187 UIKit scene-based life cycle](https://developer.apple.com/documentation/technotes/tn3187-migrating-to-the-uikit-scene-based-life-cycle) - Nota técnica de Apple para pasar una app que solo usa app delegate a `UIScene`, que las apps compiladas con el SDK de iOS 27 deben adoptar.

### Bibliotecas de estado y arquitectura

- [Swift Async Algorithms](https://github.com/apple/swift-async-algorithms) - Debounce, throttle, merge y otros operadores de `AsyncSequence` que sustituyen a los pipelines de Combine en los view models.
- [Swift Sharing](https://github.com/pointfreeco/swift-sharing) - Comparte y conserva el estado entre funciones (user defaults, archivos, memoria) mediante un único property wrapper.
- [The Composable Architecture](https://github.com/pointfreeco/swift-composable-architecture) - Reducers, effects y dependencias en una sola biblioteca, con un test store que verifica cada cambio de estado.
- [Workflow (Swift)](https://github.com/square/workflow-swift) - Máquinas de estado componibles de Square que renderizan la UI, con una biblioteca Kotlin equivalente para la app de Android.

### Inyección de dependencias

- [Factory](https://github.com/hmlongco/Factory) - Inyección basada en contenedor con registros comprobados en compilación y sustituciones por prueba, sin generación de código.
- [Needle](https://github.com/uber/needle) - Grafo de dependencias de Uber, comprobado en compilación y generado a partir del código, pensado para apps con muchos módulos.
- [Swift Dependencies](https://github.com/pointfreeco/swift-dependencies) - Inyección de dependencias al estilo environment que también funciona fuera de las vistas y sustituye valores de prueba en cada prueba.
- [Swinject](https://github.com/Swinject/Swinject) - Contenedor en tiempo de ejecución con ámbitos de objeto, habitual en bases de código UIKit que resuelven las dependencias al arrancar.

### Navegación

- [Swift Navigation](https://github.com/pointfreeco/swift-navigation) - Navegación dirigida por el estado para SwiftUI, UIKit y AppKit: un destino es un optional o un case de un enum en el modelo.
- [XCoordinator](https://github.com/QuickBirdEng/XCoordinator) - Patrón Coordinator para UIKit con rutas tipadas, para que los view controllers dejen de hacerse push entre sí.

### Apps de ejemplo

- [Clean Architecture for SwiftUI](https://github.com/nalexn/clean-architecture-swiftui) - App SwiftUI con persistencia SwiftData, red, inyección de dependencias y pruebas unitarias en capas separadas.
- [iOS Clean Architecture MVVM](https://github.com/kudoleh/iOS-Clean-Architecture-MVVM) - Plantilla UIKit con un contenedor de DI, coordinators de flujo, mapeo de DTO y caché de respuestas entre capas.
- [TCA example apps](https://github.com/pointfreeco/swift-composable-architecture/tree/main/Examples) - Casos de estudio y las apps Todos, Voice Memos, SyncUps y Search, que se mantienen al día con cada versión de la biblioteca.

### Pruebas

- [SnapshotTesting](https://github.com/pointfreeco/swift-snapshot-testing) - Guarda vistas y valores como archivos de referencia y falla si cambian, con lo que detecta regresiones de UI que las pruebas unitarias no ven.

### Estructura del proyecto y herramientas

- [Tuist](https://github.com/tuist/tuist) - Genera proyectos de Xcode a partir de manifiestos Swift, lo que mantiene explícitos los límites de los módulos a medida que crece la app.

## Flutter

### Orientación oficial

- [Architecture case study](https://docs.flutter.dev/app-architecture/case-study) - Recorre la app Compass para mostrar la guía aplicada a código real, capa por capa.
- [Architecture recommendations](https://docs.flutter.dev/app-architecture/recommendations) - Cada recomendación se califica como muy recomendada, recomendada o condicional, para que sepas qué es opcional.
- [Guide to app architecture (Flutter)](https://docs.flutter.dev/app-architecture/guide) - Las capas que recomienda el equipo de Flutter (UI, datos y dominio opcional) construidas con vistas, view models y repositories.
- [State management options](https://docs.flutter.dev/data-and-backend/state-mgmt/options) - El índice oficial de enfoques de gestión de estado, con enlaces a la documentación de cada paquete.
- [UIScene adoption](https://docs.flutter.dev/release/breaking-changes/uiscenedelegate) - Qué cambia en el runner de iOS de una app Flutter cuando `UIScene` pasa a ser obligatorio y cómo migrarlo.

### Bibliotecas de estado y arquitectura

- [Bloc](https://github.com/felangel/bloc) - Eventos de entrada, estados de salida: la lógica de negocio fuera de los widgets y probada con `bloc_test`.
- [Freezed](https://github.com/rrousselGit/freezed) - Genera clases de estado inmutables, uniones selladas y `copyWith`, y elimina el código repetitivo de los objetos de estado.
- [MobX for Dart](https://github.com/mobxjs/mobx.dart) - Observables, actions y reactions con generación de código, para equipos que prefieren el estado reactivo.
- [Provider](https://github.com/rrousselGit/provider) - Una capa fina sobre `InheritedWidget` para inyectar modelos `ChangeNotifier`; la documentación de Flutter empieza por ella.
- [Riverpod](https://github.com/rrousselGit/riverpod) - Providers seguros en compilación para estado asíncrono, caché e inyección de dependencias, que se pueden probar sin árbol de widgets.
- [Signals.dart](https://github.com/rodydavis/signals.dart) - Signals reactivas de grano fino para Dart y Flutter que reconstruyen solo los widgets que leen un valor modificado.

### Inyección de dependencias

- [get_it](https://github.com/flutter-it/get_it) - Service locator para repositories y servicios, accesible también fuera del árbol de widgets.

### Navegación

- [go_router](https://pub.dev/packages/go_router) - Enrutamiento declarativo basado en URL, mantenido por el equipo de Flutter, con deep links, redirecciones y navigators anidados.

### Apps de ejemplo

- [Bloc examples](https://github.com/felangel/bloc/tree/master/examples) - Apps de contador, temporizador, inicio de sesión, tareas, lista infinita y clima, cada una creada con bloc y cubierta por pruebas.
- [Compass app](https://github.com/flutter/samples/tree/main/compass_app) - La app de ejemplo oficial detrás de la guía de arquitectura, con pruebas unitarias, de widgets y de integración.
- [Flutter architecture samples](https://github.com/brianegan/flutter_architecture_samples) - Una misma app de tareas hecha con BLoC, Redux, MobX, signals y más, para comparar los enfoques uno al lado del otro.

### Estructura del proyecto y herramientas

- [Melos](https://github.com/invertase/melos) - Gestiona scripts, versionado y publicación en un workspace de Dart cuando una app se divide en paquetes de funciones.
- [Very Good CLI](https://github.com/VeryGoodOpenSource/very_good_cli) - Crea apps y paquetes con una estructura por capas, pruebas y lints estrictos ya configurados.

## React Native

### Orientación oficial

- [About the New Architecture](https://reactnative.dev/architecture/landing-page) - Explica Fabric, TurboModules y JSI, la arquitectura que usan por defecto las apps nuevas de React Native desde la 0.76.
- [Managing State (React)](https://react.dev/learn/managing-state) - La guía propia de React para estructurar el estado, elevarlo y pasarlo a reducers y contexto.
- [Testing overview](https://reactnative.dev/docs/testing-overview) - El mapa oficial de las pruebas unitarias, de componentes y de extremo a extremo y de qué capa de la app cubre cada una.

### Bibliotecas de estado y arquitectura

- [Jotai](https://github.com/pmndrs/jotai) - Estado atómico: compón átomos pequeños en lugar de un único store global, con átomos derivados para los valores calculados.
- [Legend-State](https://github.com/LegendApp/legend-state) - Estado reactivo de grano fino con persistencia integrada, para apps que guardan datos en el dispositivo.
- [MobX](https://github.com/mobxjs/mobx) - Estado observable con seguimiento automático de dependencias; un componente solo se vuelve a renderizar cuando cambia lo que leyó.
- [Redux Toolkit](https://github.com/reduxjs/redux-toolkit) - La forma oficial de escribir Redux: slices, actualizaciones inmutables escritas como mutaciones y RTK Query para los datos del servidor.
- [TanStack Query](https://github.com/TanStack/query) - Mantiene los datos del servidor en su propia capa, con caché, nuevas peticiones y reintentos, separada del estado de la UI.
- [XState](https://github.com/statelyai/xstate) - Máquinas de estado y statecharts para flujos con muchos estados y transiciones, como el pago o el onboarding.
- [Zustand](https://github.com/pmndrs/zustand) - Un store pequeño basado en hooks que no necesita provider; los selectores limitan los renderizados a lo que cambió.

### Navegación

- [Expo Router](https://docs.expo.dev/router/introduction/) - Enrutamiento basado en archivos para apps Expo y React Native, donde cada pantalla tiene una URL y los deep links funcionan.
- [React Navigation](https://github.com/react-navigation/react-navigation) - Navigators de stack, pestañas y drawer para React Native; Expo Router está construido sobre él.

### Apps de ejemplo

- [Ignite](https://github.com/infinitered/ignite) - Boilerplate y generadores de Infinite Red: una estructura de app completa con estado, navegación y pruebas.
- [Obytes React Native template](https://github.com/obytes/react-native-template-obytes) - Plantilla inicial de Expo y TypeScript con Expo Router, React Query, gestión de formularios y CI ya conectados.

### Pruebas

- [React Native Testing Library](https://github.com/callstack/react-native-testing-library) - Consulta los componentes como los encuentra un usuario, así que las pruebas sobreviven a las refactorizaciones del código que hay detrás de una pantalla.

## Cómo se eligen las entradas

Una entrada se añade cuando ayuda a estructurar una app y una persona la ha leído, no porque sea popular. Debe cumplir:

- ser una fuente oficial, o una biblioteca, ejemplo o artículo que muestre un patrón en código funcional;
- si es un repositorio de GitHub: no estar archivado y tener un push en los últimos 540 días;
- incluir una razón de una línea que diga, con palabras sencillas, qué obtiene el lector.

Las entradas que dejan de cumplir estas reglas se eliminan o se sustituyen. Lagunas conocidas: el material solo de Android y de Kotlin Multiplatform queda fuera del alcance, y los cursos de pago no se incluyen.
