Links sobre como estruturar um app de iOS, Flutter ou React Native: primeiro a orientação oficial e depois as bibliotecas, apps de exemplo e ferramentas que a colocam em prática. Cada item foi aberto e lido por uma pessoa e vem com uma linha dizendo o que você ganha com ele. Uma tarefa semanal sinaliza qualquer repositório listado que esteja arquivado, tenha sido renomeado ou não seja atualizado há 540 dias, e qualquer link que deixe de responder, para que a lista não apodreça em silêncio.

## Destaques

- **Três plataformas, uma estrutura** — seções de iOS, Flutter e React Native com as mesmas categorias, além dos artigos independentes de plataforma de onde vêm os padrões.
- **Um motivo para cada link** — cada item tem um "porquê" de uma linha; o verificador rejeita palavras de marketing como "melhor".
- **Verificado, não apenas coletado** — os itens ficam em [data/entries.json](data/entries.json), são validados a cada push e renderizados neste README; a atividade no GitHub e a saúde dos links são checadas toda semana ([como](docs/guides/keeping-the-list-current.md)).
- **A mesma funcionalidade em três stacks** — um [exemplo de lista de leitura](Examples/README.md) em SwiftUI, Flutter e React Native, com 43 testes que verificam as mesmas regras em cada plataforma.
- **Mudanças atuais nas plataformas** — um [guia sobre o requisito do ciclo de vida de cenas do iOS 27](docs/guides/ios-27-scene-life-cycle.md) para apps nativos, Flutter e React Native.

## Início rápido

**1. Escolha sua plataforma.** Vá para [iOS](#ios), [Flutter](#flutter) ou [React Native](#react-native). Leia primeiro os itens de *Orientação oficial*; as bibliotecas abaixo deles se baseiam nessas ideias.

**2. Execute o exemplo da sua stack.** É a menor versão funcional da estrutura que os guias descrevem:

```sh
git clone https://github.com/muhittincamdali/awesome-mobile-architecture.git
cd awesome-mobile-architecture/Examples/flutter/reading_list   # or ios/ReadingList, react-native/reading-list
flutter test                                                  # swift test, or npm ci && npm test
```

**3. Decida quanta estrutura você precisa.** [Escolhendo uma arquitetura](docs/guides/choosing-an-architecture.md) relaciona as ideias comuns às três plataformas e diz quando uma biblioteca como TCA, Bloc ou Redux Toolkit começa a compensar.

## Conceitos que valem em qualquer plataforma

### Orientação oficial

- [Guide to app architecture (Android)](https://developer.android.com/topic/architecture) - Guia do Google sobre a camada de UI, a camada de dados e o fluxo de dados unidirecional; a mesma divisão é usada no iOS, no Flutter e no React Native.
- [Presentation Model](https://martinfowler.com/eaaDev/PresentationModel.html) - O padrão de onde o MVVM surgiu: o estado e o comportamento da view mantidos em uma classe que você pode testar sem UI.
- [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) - O artigo original sobre a regra de dependência entre camadas, base da maioria dos templates de clean architecture para mobile.
- [The Elm Architecture](https://guide.elm-lang.org/architecture/) - Model, update, view: o ciclo unidirecional por trás de TCA, Redux e BLoC, explicado em poucas páginas curtas.

## iOS

### Orientação oficial

- [Discover Observation in SwiftUI](https://developer.apple.com/videos/play/wwdc2023/10149/) - Sessão da WWDC23 sobre como o Observation rastreia as propriedades que uma view lê, a base dos view models atuais do SwiftUI.
- [Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app) - Passo a passo da Apple sobre modelos `@Observable` e sobre quem os possui com `@State`, `@Environment` e `@Bindable`.
- [Migrating to the Observable macro](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro) - As edições exatas para migrar um view model `ObservableObject` para `@Observable` e como mudam as atualizações da view.
- [Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/) - Segurança contra data races, `Sendable` e isolamento de actors passo a passo: as regras a que toda arquitetura Swift 6 precisa se adequar.
- [TN3187 UIKit scene-based life cycle](https://developer.apple.com/documentation/technotes/tn3187-migrating-to-the-uikit-scene-based-life-cycle) - A nota técnica da Apple para migrar um app que usa apenas app delegate para `UIScene`, que os apps compilados com o SDK do iOS 27 precisam adotar.

### Bibliotecas de estado e arquitetura

- [Swift Async Algorithms](https://github.com/apple/swift-async-algorithms) - Debounce, throttle, merge e outros operadores de `AsyncSequence` que substituem pipelines do Combine em view models.
- [Swift Sharing](https://github.com/pointfreeco/swift-sharing) - Compartilha e persiste estado entre funcionalidades (user defaults, arquivos, memória) por meio de um único property wrapper.
- [The Composable Architecture](https://github.com/pointfreeco/swift-composable-architecture) - Reducers, effects e dependências em uma só biblioteca, com um test store que verifica cada mudança de estado.
- [Workflow (Swift)](https://github.com/square/workflow-swift) - Máquinas de estado compostas da Square que renderizam a UI, com uma biblioteca Kotlin equivalente para o app Android.

### Injeção de dependência

- [Factory](https://github.com/hmlongco/Factory) - Injeção baseada em contêiner com registros verificados em tempo de compilação e substituições por teste, sem geração de código.
- [Needle](https://github.com/uber/needle) - Grafo de dependências da Uber verificado em tempo de compilação, gerado a partir do código e feito para apps com muitos módulos.
- [Swift Dependencies](https://github.com/pointfreeco/swift-dependencies) - Injeção de dependência no estilo environment, que também funciona fora das views e troca por valores de teste em cada teste.
- [Swinject](https://github.com/Swinject/Swinject) - Contêiner em tempo de execução com escopos de objeto, comum em bases de código UIKit que resolvem as dependências na inicialização.

### Navegação

- [Swift Navigation](https://github.com/pointfreeco/swift-navigation) - Navegação orientada a estado para SwiftUI, UIKit e AppKit: um destino é um optional ou um case de enum no modelo.
- [XCoordinator](https://github.com/QuickBirdEng/XCoordinator) - Padrão Coordinator para UIKit com rotas tipadas, para que os view controllers deixem de dar push uns nos outros.

### Apps de exemplo

- [Clean Architecture for SwiftUI](https://github.com/nalexn/clean-architecture-swiftui) - App SwiftUI com persistência SwiftData, rede, injeção de dependência e testes unitários em camadas separadas.
- [iOS Clean Architecture MVVM](https://github.com/kudoleh/iOS-Clean-Architecture-MVVM) - Template UIKit com contêiner de DI, coordinators de fluxo, mapeamento de DTO e cache de respostas entre as camadas.
- [TCA example apps](https://github.com/pointfreeco/swift-composable-architecture/tree/main/Examples) - Estudos de caso mais os apps Todos, Voice Memos, SyncUps e Search, mantidos em sincronia com cada versão da biblioteca.

### Testes

- [SnapshotTesting](https://github.com/pointfreeco/swift-snapshot-testing) - Grava views e valores como arquivos de referência e falha quando mudam, detectando regressões de UI que os testes unitários deixam passar.

### Estrutura do projeto e ferramentas

- [Tuist](https://github.com/tuist/tuist) - Gera projetos do Xcode a partir de manifestos Swift, o que mantém explícitos os limites dos módulos conforme o app cresce.

## Flutter

### Orientação oficial

- [Architecture case study](https://docs.flutter.dev/app-architecture/case-study) - Percorre o app Compass para mostrar o guia aplicado a código real, camada por camada.
- [Architecture recommendations](https://docs.flutter.dev/app-architecture/recommendations) - Cada recomendação é classificada como fortemente recomendada, recomendada ou condicional, para você saber o que é opcional.
- [Guide to app architecture (Flutter)](https://docs.flutter.dev/app-architecture/guide) - As camadas recomendadas pela equipe do Flutter (UI, dados e domínio opcional), construídas com views, view models e repositories.
- [State management options](https://docs.flutter.dev/data-and-backend/state-mgmt/options) - O índice oficial das abordagens de gerenciamento de estado, com links para a documentação de cada pacote.
- [UIScene adoption](https://docs.flutter.dev/release/breaking-changes/uiscenedelegate) - O que muda no runner de iOS de um app Flutter quando o `UIScene` se torna obrigatório e como migrá-lo.

### Bibliotecas de estado e arquitetura

- [Bloc](https://github.com/felangel/bloc) - Eventos entram, estados saem: a lógica de negócio fica fora dos widgets e é testada com `bloc_test`.
- [Freezed](https://github.com/rrousselGit/freezed) - Gera classes de estado imutáveis, uniões seladas e `copyWith`, eliminando o código repetitivo dos objetos de estado.
- [MobX for Dart](https://github.com/mobxjs/mobx.dart) - Observables, actions e reactions com geração de código, para equipes que preferem estado reativo.
- [Provider](https://github.com/rrousselGit/provider) - Uma camada fina sobre o `InheritedWidget` para injetar modelos `ChangeNotifier`; a documentação do Flutter começa por ele.
- [Riverpod](https://github.com/rrousselGit/riverpod) - Providers seguros em tempo de compilação para estado assíncrono, cache e injeção de dependência, testáveis sem árvore de widgets.
- [Signals.dart](https://github.com/rodydavis/signals.dart) - Signals reativos de granularidade fina para Dart e Flutter que reconstroem apenas os widgets que leem um valor alterado.

### Injeção de dependência

- [get_it](https://github.com/flutter-it/get_it) - Service locator para repositories e serviços, acessível também fora da árvore de widgets.

### Navegação

- [go_router](https://pub.dev/packages/go_router) - Roteamento declarativo baseado em URL mantido pela equipe do Flutter, com deep links, redirecionamentos e navigators aninhados.

### Apps de exemplo

- [Bloc examples](https://github.com/felangel/bloc/tree/master/examples) - Apps de contador, timer, login, tarefas, lista infinita e clima, cada um criado com bloc e coberto por testes.
- [Compass app](https://github.com/flutter/samples/tree/main/compass_app) - O app de exemplo oficial por trás do guia de arquitetura, com testes unitários, de widget e de integração.
- [Flutter architecture samples](https://github.com/brianegan/flutter_architecture_samples) - Um mesmo app de tarefas feito com BLoC, Redux, MobX, signals e mais, para comparar as abordagens lado a lado.

### Estrutura do projeto e ferramentas

- [Melos](https://github.com/invertase/melos) - Executa scripts, versionamento e publicação em um workspace Dart quando um app é dividido em pacotes de funcionalidades.
- [Very Good CLI](https://github.com/VeryGoodOpenSource/very_good_cli) - Cria apps e pacotes com estrutura em camadas, testes e lints rigorosos já configurados.

## React Native

### Orientação oficial

- [About the New Architecture](https://reactnative.dev/architecture/landing-page) - Explica Fabric, TurboModules e JSI, a arquitetura que os novos apps React Native usam por padrão desde a 0.76.
- [Managing State (React)](https://react.dev/learn/managing-state) - O guia do próprio React para estruturar o estado, elevá-lo e movê-lo para reducers e contexto.
- [Testing overview](https://reactnative.dev/docs/testing-overview) - O mapa oficial dos testes unitários, de componente e de ponta a ponta e de qual camada do app cada um cobre.

### Bibliotecas de estado e arquitetura

- [Jotai](https://github.com/pmndrs/jotai) - Estado atômico: componha átomos pequenos em vez de um único store global, com átomos derivados para valores calculados.
- [Legend-State](https://github.com/LegendApp/legend-state) - Estado reativo de granularidade fina com persistência integrada, para apps que guardam dados no dispositivo.
- [MobX](https://github.com/mobxjs/mobx) - Estado observable com rastreamento automático de dependências; um componente só renderiza de novo quando muda o que ele leu.
- [Redux Toolkit](https://github.com/reduxjs/redux-toolkit) - A forma oficial de escrever Redux: slices, atualizações imutáveis escritas como mutações e RTK Query para dados do servidor.
- [TanStack Query](https://github.com/TanStack/query) - Mantém os dados do servidor em uma camada própria, com cache, nova busca e novas tentativas, separada do estado da UI.
- [XState](https://github.com/statelyai/xstate) - Máquinas de estado e statecharts para fluxos com muitos estados e transições, como checkout ou onboarding.
- [Zustand](https://github.com/pmndrs/zustand) - Um store pequeno baseado em hooks que não precisa de provider; os selectors limitam as novas renderizações ao que mudou.

### Navegação

- [Expo Router](https://docs.expo.dev/router/introduction/) - Roteamento baseado em arquivos para apps Expo e React Native, em que cada tela ganha uma URL e os deep links funcionam.
- [React Navigation](https://github.com/react-navigation/react-navigation) - Navigators de stack, abas e drawer para React Native; o Expo Router é construído sobre ele.

### Apps de exemplo

- [Ignite](https://github.com/infinitered/ignite) - Boilerplate e geradores da Infinite Red: uma estrutura de app completa com estado, navegação e testes.
- [Obytes React Native template](https://github.com/obytes/react-native-template-obytes) - Starter de Expo e TypeScript com Expo Router, React Query, tratamento de formulários e CI já integrados.

### Testes

- [React Native Testing Library](https://github.com/callstack/react-native-testing-library) - Consulta os componentes do jeito que um usuário os encontra, então os testes sobrevivem a refatorações do código por trás de uma tela.

## Como os itens são escolhidos

Um item é adicionado quando ajuda a estruturar um app e uma pessoa o leu, não porque seja popular. Ele precisa de:

- uma fonte oficial, ou uma biblioteca, exemplo ou artigo que mostre um padrão em código funcional;
- para um repositório do GitHub: não estar arquivado e ter recebido um push nos últimos 540 dias;
- um motivo de uma linha que diga, em palavras simples, o que o leitor ganha.

Itens que deixam de cumprir essas regras depois são removidos ou substituídos. Lacunas conhecidas: material exclusivo de Android e de Kotlin Multiplatform está fora do escopo, e cursos pagos não são listados.
