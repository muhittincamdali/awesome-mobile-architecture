Ссылки о том, как структурировать приложение на iOS, Flutter или React Native: сначала официальные рекомендации, затем библиотеки, примеры приложений и инструменты, которые применяют их на практике. Каждую запись открыл и прочитал человек, и к каждой дана одна строка о том, что вы из неё получите. Еженедельная задача отмечает любой репозиторий из списка, который заархивирован, переименован или не обновлялся 540 дней, и любую ссылку, которая перестала отвечать, чтобы список не устаревал незаметно.

## Основные возможности

- **Три платформы, одна структура** — разделы iOS, Flutter и React Native с одинаковыми категориями, а также независимые от платформы статьи, из которых происходят паттерны.
- **Причина для каждой ссылки** — у каждой записи есть однострочное «почему»; слова из маркетинга вроде «лучший» проверка отклоняет.
- **Проверено, а не просто собрано** — записи лежат в [data/entries.json](data/entries.json), проверяются при каждом push и собираются в этот README; активность на GitHub и работоспособность ссылок проверяются каждую неделю ([как](docs/guides/keeping-the-list-current.md)).
- **Одна и та же функция в трёх стеках** — [пример списка для чтения](Examples/README.md) на SwiftUI, Flutter и React Native с 43 тестами, которые проверяют одни и те же правила на каждой платформе.
- **Актуальные изменения платформ** — [руководство по требованию жизненного цикла сцен в iOS 27](docs/guides/ios-27-scene-life-cycle.md) для нативных приложений, а также приложений на Flutter и React Native.

## Быстрый старт

**1. Выберите платформу.** Перейдите к [iOS](#ios), [Flutter](#flutter) или [React Native](#react-native). Сначала прочитайте записи из раздела *Официальные рекомендации*; библиотеки ниже опираются на эти идеи.

**2. Запустите пример для вашего стека.** Это самая маленькая рабочая версия структуры, которую описывают руководства:

```sh
git clone https://github.com/muhittincamdali/awesome-mobile-architecture.git
cd awesome-mobile-architecture/Examples/flutter/reading_list   # or ios/ReadingList, react-native/reading-list
flutter test                                                  # swift test, or npm ci && npm test
```

**3. Решите, сколько структуры вам нужно.** [Выбор архитектуры](docs/guides/choosing-an-architecture.md) сопоставляет общие идеи трёх платформ и говорит, когда библиотека вроде TCA, Bloc или Redux Toolkit начинает окупаться.

## Понятия, которые работают везде

### Официальные рекомендации

- [Guide to app architecture (Android)](https://developer.android.com/topic/architecture) - Руководство Google по слою UI, слою данных и однонаправленному потоку данных; то же разделение используется в iOS, Flutter и React Native.
- [Presentation Model](https://martinfowler.com/eaaDev/PresentationModel.html) - Паттерн, из которого вырос MVVM: состояние и поведение представления хранятся в классе, который можно тестировать без UI.
- [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) - Первоисточник о правиле зависимостей между слоями, на котором основано большинство мобильных шаблонов clean architecture.
- [The Elm Architecture](https://guide.elm-lang.org/architecture/) - Model, update, view: однонаправленный цикл, лежащий в основе TCA, Redux и BLoC, — в нескольких коротких страницах.

## iOS

### Официальные рекомендации

- [Discover Observation in SwiftUI](https://developer.apple.com/videos/play/wwdc2023/10149/) - Доклад WWDC23 о том, как Observation отслеживает свойства, которые читает представление, — основа современных view model в SwiftUI.
- [Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app) - Пошаговый разбор от Apple: модели `@Observable` и то, кто ими владеет через `@State`, `@Environment` и `@Bindable`.
- [Migrating to the Observable macro](https://developer.apple.com/documentation/swiftui/migrating-from-the-observable-object-protocol-to-the-observable-macro) - Точные правки, которые переводят view model с `ObservableObject` на `@Observable`, и то, как меняется обновление представлений.
- [Swift 6 migration guide](https://www.swift.org/migration/documentation/migrationguide/) - Безопасность от гонок данных, `Sendable` и изоляция actor шаг за шагом: правила, которым должна соответствовать любая архитектура на Swift 6.
- [TN3187 UIKit scene-based life cycle](https://developer.apple.com/documentation/technotes/tn3187-migrating-to-the-uikit-scene-based-life-cycle) - Техническая заметка Apple о переносе приложения, использующего только app delegate, на `UIScene`; приложения, собранные с SDK iOS 27, обязаны перейти на него.

### Библиотеки состояния и архитектуры

- [Swift Async Algorithms](https://github.com/apple/swift-async-algorithms) - Debounce, throttle, merge и другие операторы `AsyncSequence`, заменяющие конвейеры Combine во view model.
- [Swift Sharing](https://github.com/pointfreeco/swift-sharing) - Общее состояние и его сохранение между функциями (user defaults, файлы, память) через один property wrapper.
- [The Composable Architecture](https://github.com/pointfreeco/swift-composable-architecture) - Reducer, effect и зависимости в одной библиотеке, с test store, который проверяет каждое изменение состояния.
- [Workflow (Swift)](https://github.com/square/workflow-swift) - Компонуемые конечные автоматы Square, которые отрисовывают UI, с парной библиотекой на Kotlin для приложения под Android.

### Внедрение зависимостей

- [Factory](https://github.com/hmlongco/Factory) - Внедрение через контейнер с регистрациями, проверяемыми при компиляции, и подменой для каждого теста, без генерации кода.
- [Needle](https://github.com/uber/needle) - Граф зависимостей Uber, проверяемый при компиляции и генерируемый из кода; создан для приложений со множеством модулей.
- [Swift Dependencies](https://github.com/pointfreeco/swift-dependencies) - Внедрение зависимостей в стиле environment, которое работает и вне представлений и подставляет тестовые значения для каждого теста.
- [Swinject](https://github.com/Swinject/Swinject) - Контейнер времени выполнения с областями видимости объектов; распространён в кодовых базах на UIKit, где зависимости разрешаются при запуске.

### Навигация

- [Swift Navigation](https://github.com/pointfreeco/swift-navigation) - Навигация на основе состояния для SwiftUI, UIKit и AppKit: пункт назначения — это optional или case перечисления в модели.
- [XCoordinator](https://github.com/QuickBirdEng/XCoordinator) - Паттерн Coordinator для UIKit с типизированными маршрутами, чтобы view controller больше не вызывали push друг у друга.

### Примеры приложений

- [Clean Architecture for SwiftUI](https://github.com/nalexn/clean-architecture-swiftui) - Приложение на SwiftUI с хранением в SwiftData, сетью, внедрением зависимостей и модульными тестами в отдельных слоях.
- [iOS Clean Architecture MVVM](https://github.com/kudoleh/iOS-Clean-Architecture-MVVM) - Шаблон на UIKit с DI-контейнером, coordinator для потоков, маппингом DTO и кэшированием ответов между слоями.
- [TCA example apps](https://github.com/pointfreeco/swift-composable-architecture/tree/main/Examples) - Разборы случаев плюс приложения Todos, Voice Memos, SyncUps и Search, которые обновляются вместе с каждым релизом библиотеки.

### Тестирование

- [SnapshotTesting](https://github.com/pointfreeco/swift-snapshot-testing) - Записывает представления и значения в эталонные файлы и падает при изменениях, ловя регрессии UI, которые пропускают модульные тесты.

### Структура проекта и инструменты

- [Tuist](https://github.com/tuist/tuist) - Генерирует проекты Xcode из манифестов Swift, благодаря чему границы модулей остаются явными по мере роста приложения.

## Как выбираются записи

Запись добавляется, если она помогает структурировать приложение и её прочитал человек, а не потому, что она популярна. Ей нужно:

- официальный источник либо библиотека, пример или статья, показывающие паттерн в работающем коде;
- для репозитория на GitHub: не заархивирован и есть push за последние 540 дней;
